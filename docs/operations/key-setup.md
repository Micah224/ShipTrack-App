# Key setup and token generation

Everything cryptographic in this system, in the order you actually do it: what
each secret is, how to generate it, where it has to end up, and what breaks when
it doesn't.

**First, the thing the name of this document gets wrong.** You do not generate
entitlement tokens. You generate one signing *keypair* and some secrets, then
mint *licence keys*. The token is minted by the server, on demand, when a site
calls `POST /api/v1/activate`, and refreshed twice daily by
`/api/v1/heartbeat`. There is no CLI that emits one and there is deliberately
no way to hand-write one — a token is only meaningful bound to a domain and an
install id the server assigned. Steps 1–6 below set up the machinery; step 7
mints a key; step 8 is where a token first exists.

---

## 0. The inventory

| Variable | Format | Generated by | Lives in |
| --- | --- | --- | --- |
| `ED25519_PRIVATE_KEY` | PKCS#8 PEM, newlines escaped, double-quoted | `npm run keys:generate` | Vercel only |
| `ED25519_KEY_ID` | `stp-<year><month-letter>` | same run | Vercel + `.env` |
| *(public half)* | standard base64, 32 raw bytes | same run | `TokenVerifier::PUBLIC_KEYS` in the plugin |
| `LICENSE_KEY_SECRET` | 32 bytes, standard base64 (44 chars) | same run | Vercel + `.env` |
| `GITHUB_WEBHOOK_SECRET` | 32 bytes hex | same run | Vercel + the GitHub webhook |
| `ADMIN_PASSWORD_HASH` | `scrypt.N.r.p.salt.digest` | `npm run admin:hash` | Vercel |
| `ADMIN_JWT_SECRET` | ≥32 chars | `openssl rand -hex 32` | Vercel |
| `CRON_SECRET` | any long random string | `openssl rand -hex 32` | Vercel |
| `DATABASE_URL` / `_UNPOOLED` | Postgres URLs | Neon console | Vercel + `.env` |
| `R2_ACCOUNT_ID` / `_ACCESS_KEY_ID` / `_SECRET_ACCESS_KEY` | Cloudflare | R2 API token | Vercel |
| `GITHUB_RELEASE_PAT` | fine-grained PAT, Contents: read | GitHub | Vercel |
| `ADMIN_EMAIL`, `PUBLIC_APP_URL` | plain | you | Vercel |

Three variables are read with `optional()` but behave as required, and each
fails *quietly* rather than loudly:

- `ADMIN_EMAIL` and `ADMIN_PASSWORD_HASH` — either one blank and every admin
  login is refused with `not_configured`.
- `CRON_SECRET` — unset and `/api/internal/cron/maintenance` refuses to run.
  Deliberate: better a cron that never fires than an unauthenticated endpoint
  that deletes rows.

**No stored secret may contain `$`.** Vite runs `.env` through `dotenv-expand`,
which treats `$foo` as a variable reference and substitutes it away, silently
truncating the value. Everything generated here is base64/hex and safe; a
hand-picked admin password is the one place you can trip over it.

## 1. Generate the signing pair

Once, on a machine you trust. The private key never leaves Vercel afterwards.

```bash
npm run keys:generate
```

One run prints the whole set — note the private key appears **twice**, in the
two forms that are each correct in exactly one place:

```
# Key id
ED25519_KEY_ID=stp-2026i

# Private key for .env (keep secret). The quotes and the escaped newlines are
# load-bearing here: dotenv unescapes them back into a real PEM.
ED25519_PRIVATE_KEY="-----BEGIN PRIVATE KEY-----\nMC4C…\n-----END PRIVATE KEY-----"

# Private key for Vercel (keep secret). Vercel stores values verbatim and
# unescapes nothing, so paste THIS form — real line breaks, no quotes.
# The escaped form above fails there with 'DECODER routines::unsupported'.
-----BEGIN PRIVATE KEY-----
MC4C…
-----END PRIVATE KEY-----

# Paste into TokenVerifier::PUBLIC_KEYS in the plugin (app/Licensing/TokenVerifier.php).
# Copy the whole line: the key id above and this key are one pair, and a key
# filed under the wrong id refuses every licence with 'unknown_key_id'.
    'stp-2026i' => 'WXbo…y8E=',

# Public key, PEM (for reference)
-----BEGIN PUBLIC KEY-----
…
-----END PUBLIC KEY-----

# Licence key ciphering secret
LICENSE_KEY_SECRET=…

# GitHub webhook secret
GITHUB_WEBHOOK_SECRET=…
```

It signs and verifies a probe with the pair before printing anything, and
throws rather than emitting a keypair that does not round-trip.

**Do not redirect the whole thing into `.env`** — the PHP snippet and the PEM
block are not assignments. Take only the `NAME=value` lines:

```bash
npm run --silent keys:generate > keygen.out
grep -E '^(ED25519_KEY_ID|ED25519_PRIVATE_KEY|LICENSE_KEY_SECRET|GITHUB_WEBHOOK_SECRET)=' keygen.out >> .env
```

Then read the public key line out of `keygen.out` for step 2, and shred the
file: `shred -u keygen.out` (or `rm -P`, or just `rm` — it held the private key).

### The three encodings, which are not interchangeable

This is where setups go wrong, because all three are "base64-ish":

- **`ED25519_PRIVATE_KEY`** — PKCS#8 **PEM**, printed with real newlines
  replaced by literal `\n` and the whole value wrapped in double quotes. That
  form is for `.env` **only**, where the quotes are load-bearing: both Node's
  `--env-file` and Vite's `loadEnv` unescape `\n` inside double quotes, and
  `crypto.createPrivateKey` then sees a real PEM.

  **Vercel is different.** Environment variables there are stored verbatim —
  nothing unescapes anything — so paste the *real multi-line PEM* into the
  value box, with actual line breaks and no surrounding quotes. Reconstruct it
  from the printed line by dropping the quotes and turning each `\n` back into
  a newline, or take the PEM straight from `keygen.out`. Paste the escaped form
  and every signing attempt fails with
  `error:1E08010C:DECODER routines::unsupported`, which names nothing useful.
- **the plugin constant** — standard base64 of the **raw 32 bytes**, *with* `=`
  padding (`SODIUM_BASE64_VARIANT_ORIGINAL`). Not PEM. Not base64url. A PEM blob
  here fails with `bad_public_key`.
- **token segments** — base64url, unpadded. A different variant again, and not
  something you ever paste anywhere.

`LICENSE_KEY_SECRET` is exactly 32 bytes of standard base64 (44 characters);
anything else throws `LICENSE_KEY_SECRET must be 32 bytes, base64-encoded.`

## 2. Paste the public key into the plugin

In `ShipTrack-Pro/app/Licensing/TokenVerifier.php`:

```php
public const PUBLIC_KEYS = [
    'stp-2026i' => 'WXbowSLcfiYMJquWJjdmCQpfuWvfdT2PSE0JPnlLy8E=',
];
```

The array key is the `kid`, and it must be the one from the *same* generator
run. The generator prints the whole line ready to paste for exactly this
reason: a key filed under a mismatched id makes every site refuse its licence
with `unknown_key_id`, while the server looks perfectly healthy.

This constant ships empty in a fresh checkout, and the empty case is checked
*first* in `verify()`, before the token is even parsed. Until you paste a key,
every licence on every site reads as invalid with reason `no_public_key`,
surfacing on the Licence screen as `unverifiable:no_public_key`.

Sanity check the string you pasted, using the same call the plugin makes:

```bash
php -r 'var_dump(strlen(sodium_base642bin("PASTE_HERE", SODIUM_BASE64_VARIANT_ORIGINAL)) === SODIUM_CRYPTO_SIGN_PUBLICKEYBYTES);'
```

`bool(true)` means it decodes to 32 bytes. That proves the encoding, not that
it is the *right* key — step 9 proves that.

## 3. The remaining secrets

**Admin console password.** Never typed on a command line where it lands in
shell history:

```bash
read -rs PW && printf '%s' "$PW" | npm run admin:hash
```

Twelve characters minimum. The output looks like
`scrypt.32768.8.1.<salt>.<digest>` — six fields, `.`-separated, salt and digest
base64url. The separator is `.` and not the conventional `$` because
`dotenv-expand` would eat `$32768` and `$8`, truncating the hash so that every
login fails while the same hash verifies fine from a Node CLI.

Only the digest is stored; the plaintext password exists nowhere.

**Session signer and cron bearer:**

```bash
echo "ADMIN_JWT_SECRET=$(openssl rand -hex 32)"
echo "CRON_SECRET=$(openssl rand -hex 32)"
```

`ADMIN_JWT_SECRET` must be at least 32 characters and is used as raw UTF-8
HMAC bytes — it is not decoded from hex, so 64 hex characters is simply a
64-byte key. Hex also guarantees no `$`.

**Neon** — both URLs from the project's connection details: the pooled one for
the running app, the direct/unpooled one for `drizzle-kit` and the mint CLI.

**R2** — an API token scoped to `shiptrack-app-store` with object read/write.

**GitHub** — a fine-grained PAT with `Contents: read` on `Micah224/ShipTrack-Pro`,
and the same `GITHUB_WEBHOOK_SECRET` on both sides of the `release.published`
webhook.

## 4. Database

The Neon default branch may still carry the superseded 2026-08-31 schema
(`orders`, `rate_buckets`, `customer_identities`, `admin_audit`). It collides
with `0000_init_licensing`, and **`drizzle-kit migrate` reports that collision
only as exit code 1, printing nothing at all** — so a silent failure here looks
like success.

Check first that there is nothing to lose:

```sql
SELECT
  (SELECT count(*) FROM customers) AS customers,
  (SELECT count(*) FROM licenses)  AS licenses,
  (SELECT count(*) FROM orders)    AS orders;
```

All three must be zero. If they are not, stop and work out why. Then run
`scripts/reset-legacy-schema.sql` and migrate:

```bash
DATABASE_URL_UNPOOLED='postgres://…' npm run db:migrate
```

The variable has to be exported on that command. Unlike the three operator
CLIs, `db:migrate` carries no `--env-file-if-exists` and does not go through
`vite.config.ts`, so it will not pick up `.env` the way the rest of the tooling
does.

## 5. Vercel

Set every variable from the inventory on the **Production** environment, then
deploy. `PUBLIC_APP_URL` must be the origin customer sites can actually reach —
it is baked into the download and asset URLs handed to WordPress.

The plugin's compiled-in default is `https://ship-track-app.vercel.app`
(`LicenseClient::DEFAULT_BASE`), so add that hostname to the project's domains.
If you would rather use a different origin, override it per-site with the
`shiptrack_pro/license_api_base` filter; the constant is the fallback, not a
hard requirement.

Verify the deployment is answering before you touch a real site:

```bash
curl https://ship-track-app.vercel.app/api/v1/heartbeat
# {"ok":true,"service":"shiptrack-licence","ready":true}
```

A `DEPLOYMENT_NOT_FOUND` body means the domain is attached to no production
deployment, not that the code is broken.

## 6. Mint a licence key

```bash
npm run license:mint -- --email customer@example.com --name "Customer Ltd" --tier PROFESSIONAL
```

| Flag | Required | Default |
| --- | --- | --- |
| `--email` | yes | — |
| `--name` | yes | — |
| `--tier` | no | `STARTER`; one of `STARTER`, `PROFESSIONAL`, `ENTERPRISE` |
| `--seats` | no | 1 / 3 / 25 by tier |
| `--expires` | no | empty means lifetime |

It writes to the database over the **unpooled** connection, so
`DATABASE_URL_UNPOOLED` (or `DATABASE_URL`) and `LICENSE_KEY_SECRET` must both
be set. It creates the customer if the email is new, inserts the licence, and
records a `license.mint` audit row.

The key looks like `STP-4F2A-9K7M-2XQR-8VNB-3HTY-6JWD-5PGZ-…` — Crockford
base32, so no I, L, O or U to misread over the phone.

**The plaintext key is printed once and never again.** The database holds only
its sha256 (for lookup) and an AES-256-GCM ciphertext, plus the first two groups
in the clear so support can identify it. Lose it and the only remedy is minting
another.

## 7. Generate a token — that is, activate a site

On the customer's site, **ShipTrack Pro → Licence**
(`/wp-admin/admin.php?page=shiptrack-pro-license`), paste the key, submit. That
is the whole interface: one field. Domain and install id are derived, never
typed.

Scripted equivalent, as a user holding `MANAGE_SETTINGS` — note the REST
namespace is `wpls/v1`:

```bash
curl -X POST https://customer.example/wp-json/wpls/v1/license \
  -H 'content-type: application/json' \
  --user 'admin:APPLICATION_PASSWORD' \
  -d '{"key":"STP-…"}'
```

What happens underneath: the plugin POSTs to `/api/v1/activate` with `key`,
`site_url`, `install_id`, `plugin_version`, `wp_version`, `php_version` and a
`nonce`. The server binds the licence to that domain and install and returns

```json
{"ok":true,"token":"…","payload":"…","kid":"stp-2026i","expires_at":…,
 "state":"ACTIVE","environment":"PRODUCTION","counts_seat":true,
 "seats":{"used":1,"total":3}}
```

The plugin **verifies the token before storing it**, so a misconfigured server
cannot park an unverifiable token on the site. `token` is the full three-part
entitlement; `payload` is the base64url payload segment, i.e. the exact bytes
that were signed. The plugin verifies over those bytes and never re-encodes
them: PHP escapes `/` as `\/` and non-ASCII as `\uXXXX` where JavaScript does
neither, so a re-encoding client works for plain-ASCII customers and fails only
for the ones whose data carries a URL or an accent.

Two things bind the token, and both are worth knowing for support:

- **Domain** — the punycode-normalised host of `home_url()` (not `site_url()`),
  lowercased, trailing dot and leading `www.` stripped. An internationalised
  domain is compared as `xn--…` on both sides.
- **Install id** — a UUIDv4 in the `stp_license_install` option, minted once and
  never regenerated, not even when the key changes. Read it with
  `wp option get stp_license_install`. Deleting it orphans the seat on the
  server and forces a re-activation.

Tokens expire after `TOKEN_TTL_DAYS` (7) and the twice-daily
`stp_license_heartbeat` cron refreshes them. If the server is unreachable the
site keeps working through a 7-day grace period; revocation and suspension
bypass grace entirely.

## 8. Prove the two halves are actually mated

The plugin's own test suite generates fresh keypairs, so it proves the
*verifier* — it says nothing about whether the key you pasted matches the key
Vercel signs with. This does. Sign a probe in the platform repo:

```bash
# Written into the repo root, so the relative import below resolves.
cat > sign-probe.ts <<'TS'
import { signLicenseToken } from './src/lib/server/crypto/ed25519.ts';
const now = Math.floor(Date.now() / 1000);
console.log(JSON.stringify(signLicenseToken({
  v: 1, sub: 'sha256:' + 'a'.repeat(64),
  domain: 'probe.example.com', install: 'probe-install',
  tier: 'PROFESSIONAL', features: ['road', 'https://example.com/münchen'],
  status: 'ACTIVE', seats: { used: 1, total: 3 },
  limits: { branches: 5, auditRetentionDays: 90 },
  exp: now + 604800, iat: now, nbf: now - 60, nonce: 'probe'
})));
TS
node --env-file=.env --experimental-strip-types ./sign-probe.ts > /tmp/token.json
rm sign-probe.ts
```

and verify it in the plugin repo against the compiled-in constant:

```bash
php -r '
require "app/Licensing/TokenVerifier.php";
$d = json_decode(file_get_contents("/tmp/token.json"), true);
$r = (new \ShipTrackPro\Licensing\TokenVerifier())->verify($d["token"], "probe.example.com", "probe-install");
echo $r["reason"], PHP_EOL;
'
```

`ok` means the pair is mated and every encoding is right. Anything else names
which of the checks below failed. The non-ASCII feature string in the probe is
deliberate: it is what catches a client that re-encodes the payload.

## 9. When it refuses: what each reason means

`TokenVerifier` returns one of these, checked in this order.

| Reason | Cause |
| --- | --- |
| `no_public_key` | `PUBLIC_KEYS` is still empty. Step 2. |
| `malformed` | Not three dot-separated parts. Truncated in transit or storage. |
| `bad_header` | `typ` is not `STP-LIC` or `alg` is not `Ed25519`. Not our token. |
| `unknown_key_id` | The token's `kid` has no entry in `PUBLIC_KEYS`. Key rotated on the server without shipping a plugin build that carries the new key — or the kid drift in step 2. |
| `bad_public_key` | The pasted string is not standard base64 of 32 bytes. PEM pasted instead of the raw key, or base64url instead of base64. |
| `bad_signature_encoding` | Signature segment is not 64 bytes of base64url. |
| `bad_signature` | The key does not match the one that signed, or a byte changed. This is what a *wrong but well-formed* key looks like. |
| `bad_payload` / `unsupported_version` | Payload is not JSON, or `v` is not 1. Server and plugin are different generations. |
| `domain_mismatch` | Token bound to a different host. Site moved, or `home_url()` and the activated URL disagree. Re-activate. |
| `install_mismatch` | `stp_license_install` changed. Usually a restored or cloned database. Re-activate. |
| `not_yet_valid` / `expired` | Clock drift beyond the 300-second tolerance, or a token older than `TOKEN_TTL_DAYS` with a heartbeat that has not run. |

Other codes you will see, from layers above the verifier:

| Code | Cause |
| --- | --- |
| `unverifiable:<reason>` | Activation reached the server but the returned token failed the check above. The token is *not* stored. |
| `transport_error` | The site could not reach the API at all. Check `LicenseClient::DEFAULT_BASE` resolves, or set the `shiptrack_pro/license_api_base` filter. |
| `unknown_key` (404) | The server has no licence with that key hash. |
| `seat_limit_reached` (403) | All seats in use. Deactivate one, or raise `max_seats`. |
| `decryption_failed` | The stored key or token cannot be decrypted — WordPress salts were regenerated. Re-enter the key. |
| `not_configured` | `ADMIN_EMAIL` or `ADMIN_PASSWORD_HASH` is blank. |
| `rate_limited` | Ten failed admin logins from one address in fifteen minutes. The correct password is refused too until the window passes. |

## 10. Rotating the signing key

`PUBLIC_KEYS` holds more than one entry precisely so this needs no flag day:

1. `npm run keys:generate` — new key, new `kid`.
2. Add the new entry to `PUBLIC_KEYS` **alongside** the old one, and ship that
   plugin release. Sites now accept both.
3. Once enough sites have updated, set the new `ED25519_PRIVATE_KEY` and
   `ED25519_KEY_ID` in Vercel. Tokens issued from here carry the new `kid`;
   existing tokens keep verifying until they expire.
4. A release later, drop the old entry.

Doing 3 before 2 refuses every licence on every site that has not updated.
